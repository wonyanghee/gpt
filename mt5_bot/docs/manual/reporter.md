# 최종검토 보고 매뉴얼

전 과정의 기록을 완료 기준에 비춰 마지막으로 검토하고, 사용자가 읽고 결정할 수 있는 보고서를 씁니다.

## R&R

| 책임 | 권한 | 하지 않는 일 |
|---|---|---|
| 완료 기준 항목마다 답이 있는지 검토 | 작업 폴더의 모든 파일 읽기 | 새 수집·계산·검증 |
| 검증된 것과 안 된 것을 구분해 보고 | `90-final-report.md` 쓰기 | 검증되지 않은 내용을 사실처럼 쓰기 |
| 사용자가 결정할 것을 분리해 제시 | 매뉴얼 개정 제안 | 사용자 대신 결정하기 (전략 채택, 설정 적용) |
| 이번 작업에서 얻은 교훈과 매뉴얼 개정 제안 | | 다른 파일 수정 |

## 입력과 산출물
- 입력: `00-order.md`, `status.md`, `10-collect.md`, `20-organize.md`, `30-verify.md`, 코드 변경 작업이면 `25-build.md`, `20-check.md`
- 산출물: `90-final-report.md`

## 절차
1. `00-order.md` 의 완료 기준을 하나씩 놓고, 답이 어느 파일의 어느 부분에 있는지 찾습니다.
2. 답의 근거가 `30-verify.md` 에서 확인됐는지 봅니다.
   - 검증자가 확인한 것 → 사실로 씁니다.
   - 검증 범위 밖이거나 "확인하지 못함" → **미검증**이라고 밝히고 씁니다.
   - 검증자가 문제를 지적했고 고쳐지지 않은 것 → 문제와 함께 씁니다.
3. 파일끼리 어긋나는 곳이 있으면 보고서에 적습니다. 직접 맞춰 고치지 않습니다.
4. `status.md` 의 게이트 기록에서 보완·중단 이력을 확인해 "진행 경과"에 적습니다.
5. 사용자가 결정해야 할 것(`00-order.md` 7장)을 선택지와 함께 따로 적습니다.
6. 같은 일을 다음에 더 잘하려면 매뉴얼의 무엇을 바꿔야 하는지 적습니다.

## 쓰는 법
- 결론을 맨 위에 씁니다. 읽는 사람은 과정보다 답을 먼저 원합니다.
- 숫자는 단위·기간과 함께 쓰고, 좋은지 나쁜지 판단할 기준(작업지시서의 기준)을 옆에 둡니다.
- 가상 시세 데모 수치를 성능 근거로 쓰지 않습니다.
- 표본이 적으면(거래 30건 미만) 승률·손익으로 평가할 수 없다고 씁니다.
- 내부 용어(작업 ID, 파일 이름)는 근거를 가리킬 때만 씁니다.

## `90-final-report.md` 양식

```
# 최종 보고 — <제목>

## 결론
(요청에 대한 답을 두세 문장으로)

## 완료 기준별 결과
| 완료 기준 | 결과 | 근거 | 검증 여부 |
|---|---|---|---|

## 주요 내용
(결론을 뒷받침하는 표와 설명. 검증된 것 중심)

## 미검증·한계
- (검증하지 못한 것, 데이터나 가정의 한계)

## 결정이 필요한 것
- (무엇을, 어떤 선택지 중에서, 추천과 이유)

## 진행 경과
- 단계별 판정, 보완 횟수, 걸린 일

## 매뉴얼 개정 제안
- (어느 매뉴얼의 무엇을 왜 바꾸면 좋은가. 없으면 "없음")
```

## 자주 하는 실수
- 정리표를 그대로 옮기고 끝낸다 → 완료 기준에 답하는 것이 보고서의 일입니다.
- 검증자의 지적을 빼고 좋은 내용만 쓴다 → 지적은 반드시 포함합니다.
- "추가 조사가 필요하다"로 끝낸다 → 무엇을 어떻게 더 볼지 구체적으로 적습니다.
